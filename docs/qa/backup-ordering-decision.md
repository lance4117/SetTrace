# 备份数组顺序：已确认的设计补充

状态：2026-10-17 用户已确认采用；纳入提案并实施 v5→v6 追加迁移。

## 冲突与复现

当前 v1 协议把计划数组顺序视为业务内容，恢复必须保留数组顺序与 createdAt。
现有数据库列表只按 created_at ASC、id ASC 排序。例：备份先列“计划 B”（创建时间 200），
再列“计划 A”（创建时间 100），两项字段与摘要均合法；插入后查询却返回 A、B，导致核心
摘要不同并回滚。修改时间、静默重排或把合法文件临时归类为损坏均不能满足提案。
历史数组同样应考虑 startedAt 与数组顺序不同（例如时钟回拨）的情况。

## 已采用补充

1. 为 plans 增加独立整数 sort_order；迁移时按现有 created_at/id 列表顺序填充，
   保持升级前后的页面顺序、名称和创建时间。新计划与计划导入按末尾追加分配序号。
2. 为 workout_sessions 增加独立的备份序列字段；旧完成记录按当前快照查询顺序初始化，
   新保存的训练追加序号。历史页面仍按训练日期展示，备份序列不改变日期与统计口径。
3. 完整恢复按目标数组写入上述序列；动作、组、完成次序及跳过批次保持既有字段与引用。
4. 为保留已存在的 v5 测试安装，采用 v5→v6 追加迁移；原生提醒明确支持 v4/v5/v6，不自行迁移。
5. 同步 design §5、数据库说明和任务条件，补充逆时间数组、同时间并列、旧版本迁移、
   普通新建／导入追加、恢复→新增→撤回的顺序测试。

目标是不改变用户时间与已存历史事实，仅使协议承诺的顺序有对应的持久化表示。
不增加“手动拖动计划排序”产品功能，不修改计划分享格式。
