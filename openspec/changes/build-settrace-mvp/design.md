# Design

## Context

参见 `proposal.md`。仓库当前没有 Flutter 源码或已有数据，只有空的 OpenSpec 能力目录，以及 `docs/design/SetTrace_UI_Design_System_and_Flutter_Spec.md`、浅色/深色高保真图和 Token 图。第一目标是 Android 竖屏；核心流程必须离线运行，不依赖账号。训练中断后恢复和休息时间准确性比通用架构更重要。

## Goals / Non-Goals

**Goals:**

- 用少量清晰的 Flutter 模块完成一条可持续使用的训练闭环。
- 每个改变训练进度的操作先可靠落库，再更新界面；计划变动不污染会话和历史。
- 同一套组件根据语义色切换浅色/深色，在 Android 16 和常见 360–430 dp 竖屏上可用。

**Non-Goals:**

- 通用动作库、肌群分类、逐组重量/次数、动作备注、云同步、后台通知和复杂时长预测。设计说明提到可选备注，但高保真编辑页没有对应入口，且用户的 MVP 核心字段未要求它，因此留待后续变更。
- 为未来平台预先建立多数据库实现、同步协议或完整 Clean Architecture 分层。

## Decisions

### 1. Flutter 工程与模块边界

新建标准 Flutter 应用和 Android 工程。`app/` 放根导航与主题，`core/database/` 放 SQLite 初始化和迁移，`core/widgets/` 只放实际跨页面复用的组件；`features/plans/`、`features/workout/`、`features/history/`、`features/settings/` 分别放页面、简单状态对象和数据操作。导航使用 `MaterialApp`、根部三个 Tab 和普通 Navigator 路由；训练中/休息中是同一会话页面的两种状态，避免反复入栈。状态由少量 `ChangeNotifier` 管理，不引入全局事件总线。相较一开始采用通用路由和分层框架，这样更容易定位个人项目的问题。

### 2. 本地数据与快照

使用 SQLite（Android 首版可由 `sqflite` 提供），为未来跨平台迁移把 SQL 封装在少量 repository 中。主题偏好可用轻量键值存储。首版数据库版本为 1，包含：

| 表 | 主要字段 |
|---|---|
| `plans` | `id`, `name`, `created_at`, `updated_at` |
| `plan_exercises` | `id`, `plan_id`, `name`, `sort_order`, `target_sets`, `rest_between_sets_seconds`, `rest_after_exercise_seconds`, `default_weight_kg` |
| `workout_sessions` | `id`, `source_plan_id`（可空）, `plan_name_snapshot`, `started_at`, `started_local_date`, `ended_at`, `duration_seconds`, `status`, `current_exercise_order`, `current_set_number`, `rest_kind`, `rest_started_at`, `rest_end_at` |
| `session_exercises` | `id`, `session_id`, `source_exercise_id`（可空）, `name_snapshot`, `sort_order`, `target_sets`, 两种休息秒数, `default_weight_kg` |
| `session_sets` | `id`, `session_exercise_id`, `set_number`, `completed_at`（可空） |

外键开启并对会话、日期和顺序建立必要索引；进行中会话通过数据库约束或事务保证最多一条。计划删除时来源 ID 置空，快照和历史不级联删除。动作名称无需固定类型；重复名称允许。休息时长用非负整数秒、按 30 秒档位输入；可选重量只是计划提示，训练时不产生逐组重量记录。时间戳使用统一的 UTC 时间值，训练日期在开始时按设备本地日历写入，跨午夜训练归开始日。

与把计划 JSON 直接塞进一条会话记录相比，五张表便于按组撤销、修改目标组数和统计，同时仍足够小；不建立通用 ORM 实体体系。

### 3. 训练状态转换与事务

开始训练时，在一个事务内复制有序动作、目标组数和待完成组行。界面游标使用 1 起始的动作顺序与组序号；持久化操作包括完成组、撤销、修改本次目标组数/后续休息参数、跳过或调整休息、结束训练。每次事务同时维护组行、游标、休息字段；加载时若游标与按组记录不一致，以已持久化的组记录重建并修复游标。

完成非最后一组时游标指向下一组，使用组间休息；完成动作最后一组且仍有下一动作时游标指向下一动作首组，使用动作后休息；全场最后一组不再启动休息，进入结束确认。休息为 0 时直接显示下一组。快速连续点击通过操作中的按钮禁用和数据库状态校验只计一次。撤销最近一组会清除当前休息并回到该组。本次目标组数修改只增加待完成组或删除未完成的尾部组，不能小于已完成数；修改休息配置只影响后续休息，不改当前已启动的截止时间。

提前结束默认提供“继续 / 保存已完成 / 丢弃”选择；已有完成组时丢弃再单独确认，零完成组会话确认后直接丢弃。保存时写入结束时间与实际时长，部分完成会话进入历史。实际时长采用开始到结束的经过时间，包含休息和后台时间；首版不支持暂停。相较自动在最后一组后立即关闭会话，明确确认能减少误触损失。

### 4. 休息计时与恢复

开始休息时一次写入 `rest_started_at`、`rest_end_at` 和类型（组间/动作间）。前台每秒仅刷新显示，剩余秒数始终从 `rest_end_at - now` 计算，不按 tick 递减数据库值。±30 秒修改持久化的截止时间；减到零或跳过清除休息并显示游标指向的组。应用启动和从后台返回时查询唯一未完成会话；若截止时间已经过去，归一化为可开始下一组。首版不申请通知或精确闹钟权限。

### 5. 页面与视觉实现

根 Tab 为计划、记录、设置。计划卡进入详情，详情可编辑动作与排序并进入准备页；准备页展示确定的动作数、组数和顺序，点击开始才创建会话。训练页保持 Figma 的当前动作、大组数、进度点、主要按钮和下一动作卡片，另加完整列表入口与明确的结束处理。休息状态沿用大倒计时和三个操作按钮。记录页在 Figma 月度统计上补本周次数、按日列表和详情；设置页先做主题切换。

以 `ThemeData` 配合 `ThemeExtension` 管理语义色；浅/深稿共享尺寸、布局和 Widget。先实现按钮、卡片、Picker、导航、动作行、进度点与倒计时等多处共用元素，避免一次预建完整组件库。Picker 吸附档位，仅有效档位变化触发轻触反馈。手机外框、模拟状态栏不进入正式页面；对齐 Android 安全区域和返回手势。设计稿中的“预计时长”在没有明确计算规则前不展示，避免伪精确。

### 6. 历史与统计口径

历史只查询已保存会话，按 `started_local_date` 分组，同日多次分别列出。详情由快照和实际完成组行组成。最近一次按结束时间排序；本周从本地周一开始，本月按本地自然月计算，次数以会话数计；总时长与完成组数为简单求和。避免引入训练算法和预计算统计表。

## Risks / Trade-offs

- [App 被系统杀掉或用户连点] → 每次状态转换使用事务；训练数据不只留在内存；关键按钮在写入期间禁用。
- [设备时钟被手动修改] → 绝对时间倒计时可能跳变；恢复时将负剩余时间归零，首版不构建额外时钟校准机制。
- [用户让训练跨夜保持未完成] → 实际时长会包含长时间后台停留；恢复入口明确显示原训练并允许结束，不自动结束或伪造训练时长。
- [卸载 App 或设备损坏] → 纯本地数据可能丢失；首版不承诺备份，导出/备份另立变更。
- [未来 Web/桌面支持] → `sqflite` 首版侧重 Android；数据库访问集中在 repository，未来可更换适配层，不让 UI 依赖 SQL。
- [设计稿未覆盖所有产品操作] → 用相同 Token 和组件补齐结束确认、完整动作列表、记录详情；功能验收优先于逐像素照搬。

## Migration Plan

项目尚无旧版本与用户数据。创建 Flutter 工程后建立数据库 v1；后续字段变更采用显式版本迁移，不在发布版中删除数据库重建。开发阶段可重置本地测试数据；首版发布后回滚应用二进制不保证旧版本能读取较新数据库，因此迁移必须向前兼容并在升级测试中验证。
