# Design

## Context

变更动机见 `proposal.md`，行为契约见两份 delta specs。当前会话用 `current_exercise_order` 和数组下标定位动作，`completeSet()` 通过序号 +1 查找后继；`_repairCursor()` 按排序寻找第一个未完成组，可能清除不匹配的休息。动作列表的编辑权限也依赖序号，而非组记录状态。

SQLite v1 的 `session_exercises.id` 与 `session_sets.session_exercise_id` 已提供稳定身份，且存在 `UNIQUE(session_id, sort_order)`。计划排序已有“先临时负序号、后最终正序号”的事务模式可参考，但不能调用计划排序方法修改本次会话。历史通过仓库按 `sort_order` 加载并展示，因此最终会话顺序可以直接复用。

现有版本只记录组完成，没有组开始事件；本次以“零完成组”作为可移动条件，不声称能识别实际动作开始。倒计时保持当前截止时间设计，不承接已撤回的 timer 修复。

## Goals / Non-Goals

**Goals:**
- 把动作身份、展示顺序、完成状态分开，排序不迁移组记录到其他动作。
- 在一个事务内保存合法顺序和对应游标，支持恢复、撤销、部分保存及原计划删除后的独立训练。
- 明确可排序规则与界面保存边界，避免拖动中间状态直接影响训练。

**Non-Goals:**
- 不为动作新增手动开始状态、计时片段或切换时间线。
- 不支持部分完成动作之间来回切换，不改动主导航和计划编辑流程。
- 不重构通用倒计时或引入全应用状态管理框架；只协调新增排序提交与现有会话加载。

## Decisions

### 1. 使用稳定当前动作 ID，并保留序号投影

数据库 v2 为 `workout_sessions` 增加可空 `current_session_exercise_id INTEGER`，保存 `session_exercises.id`；仓库在每次写入时校验该 ID 属于当前会话。保留 `current_exercise_order` 作为派生展示字段，同一事务同步维护，避免旧模型、统计 fixture 和读取代码一次性全部失效。模型按 ID 查找当前动作，不再把顺序当作身份。有效当前组未完成时保持其 ID；当前动作未完成组被修改完或动作完成时，再选本次排序中下一未完成动作。

替代方案是继续仅保存序号、每次排序重新推导 ID，但过期的“序号 2”可能已经指向另一个动作，也使恢复与撤销更容易误定位。稳定 ID 解决这一身份歧义，序号仍服务于展示与排队。

完成组提交使用预期动作 ID 和组号校验，禁止旧 B 页面在排序后将相同序号的 C 标为完成。排序提交还携带打开界面时的顺序、当前 ID/组号和组完成状态摘要，在事务内与最新状态比较；变化时整次拒绝并重新加载，不自动合并旧草稿。

### 2. 根据组记录确定可移动集合，锁定其他位置

可移动动作必须零完成组；已完成或部分完成动作锁定在原位置。完整排序以现有全列表为基础，仅将用户选定的零完成组动作排列填回它们原先占用的槽位，其他动作保持位置。这样撤销后出现的非连续状态也不要求假设“序号之前必然完成”。

“更换下一动作”将选中候选移到可移动集合首位，其余候选保持相对顺序。当当前动作零完成组时，候选首位成为当前第一组；当前动作部分完成时保持其 ID/组号，首位候选仅决定它做完后去哪里。撤销后若动作变为零完成组，就重新进入可移动集合；仍有完成组则继续锁定。

完整排序提交必须包含每个可移动 ID 恰好一次；拒绝跨会话、重复、缺失或锁定动作移动。用负序号暂存再写正序号，事务内同步当前 ID、组号、序号，失败整体回滚。快照动作配置、组行和完成时间不更新，原计划表不参与事务。

只改 UI 列表无法满足数据库唯一约束、重启及组归属；立即把拖动结果逐次落库会增加误操作，因此排序采用草稿 + 显式保存。

### 3. 进度、撤销和恢复按身份与状态处理

后继动作从本次顺序的未完成集合中寻找，不再盲取序号 +1；组数编辑权限基于“未完成”与当前 ID，避免错误锁定排在其他位置的未完成动作。部分完成当前动作始终继续其下一未完成组。有效 ID 和组号在恢复时保持；只有失效、错误归属或已完成的游标才按组记录修复，随后同步序号投影。全部组完成时保留合法的最后动作引用供结束确认，不创建新休息。

撤销定位最近有效完成事件，取消该组的完成记录及关联休息，但不撤回排序。为避免排序后不同动作的完成时间恰好相同时按数据库行 ID 误判先后，v2 为 `session_sets` 增加可空 `completed_sequence INTEGER`。完成组时在会话事务中分配当前最大有效序号 +1；撤销按该序号倒序，清除时间及序号。此字段仅用于确定完成事件顺序，不新增产品字段或历史时间线。

旧组记录按完成时间、原组 ID 确定性回填序号；旧版相同时间戳的真实先后无法补推，因此保留旧版的同时间戳处理顺序。新记录能够明确区分；迁移不修改已有时间戳。

### 4. 换序保留正在进行的休息

排序不清除或重写 `rest_kind`、`rest_started_at`、`rest_end_at`；在保存前只沿用现有到期判断，已到期则正常退出休息，尚未到期则保留截止时间。A 完成后的休息来自 A，换成 C 不能使用 C 的休息值重算。组间休息中的排序只调整后续待练集合，不改变当前部分完成动作。

主动跳过、±30 秒和撤销仍遵守各自原有规则。排序不会自动触发这些操作。正常恢复会通过同步后的 ID 与组号认定游标有效，避免把合法排序当作游标损坏而清除休息。

### 5. 最小界面扩展与提交协调

- 训练页的下一动作区域、动作间休息页提供“更换下一动作”。当前零完成组时说明“替换当前待练动作”；当前部分完成时说明“当前动作做完后练”，使选择含义清楚。
- “全部动作与编辑”增加排序模式，标明“已完成”“进行中”“待练”，锁定行无拖动手柄；允许拖动待练项，并提供保存、取消和“只影响本次训练”说明。
- 不足两个候选时隐藏或禁用换序入口；零休息动作切换后的训练页同样能选择。
- 排序草稿不写数据库。打开时保留状态摘要，保存中禁用重复提交及训练写操作；生命周期恢复或其他操作改变状态时拒绝旧草稿并刷新。迟到的排序前加载结果不得覆盖保存后的列表。
- 提交失败保留持久化状态，显示错误并提供重新加载；模态界面有明确取消出口，不遮挡系统安全区域。

继续使用现有组件、语义色和至少 48 dp 触控区域，验证 360–430 dp 竖屏与字体缩放，不引入新 UI 依赖。

### 6. 历史保存最终会话排序

历史沿用 `session_exercises.sort_order`，展示最终会话快照中的动作顺序和组状态。它是本次排序结果，不是包含每次撤销与重做的完整执行时间线。部分保存仍展示未完成动作与组；统计继续使用原完成组数与整场时长口径。原计划删改不影响会话或历史。

## Risks / Trade-offs

- [已开始做第一组但尚未点完成，App 无法感知] → 以零完成组定义可移动范围，界面说明换序不会记录该组，不添加计时或开始按钮。
- [排序后旧序号仍被当作动作身份] → 逐条检查完成、编辑、撤销、恢复和详情路径，使用 ID 校验，并增加旧界面提交被拒绝的测试。
- [排序保存造成休息丢失或重置] → 事务保留尚未到期的休息字段，测试换序前后截止时间完全一致，包括已做 ±30 秒调整的情况。
- [升级损坏已有训练数据] → 使用真实 v1 数据库 fixture 验证新建与升级、进行中两类休息、已保存及部分保存历史、损坏旧游标；迁移失败回滚，不删库重建。
- [撤销导致完成与待练行交错] → 候选依据组状态，锁定行槽位保持；推进跳过已完成项，测试连续跨动作撤销及再次排序。
- [旧版无法直接打开 v2 数据库] → 回退需发布仍支持 v2 的修复包；不依赖直接安装旧版或删除新字段。

## Migration Plan

1. 将数据库版本升到 2，通过 `onUpgrade` 非破坏性增加当前 ID 和完成序号字段；新建数据库最终结构与升级结果一致。不为当前 ID 增加反向外键，避免与动作表现有级联关系形成循环；仓库事务负责同会话归属校验。
2. 对进行中的旧会话，先按 v1 固定顺序的首个未完成组核对旧游标；一致时将旧 `current_exercise_order` 映射为本会话动作 ID，保持原组号和休息字段。不匹配或无映射时按已有纠错规则修复并处理不对应的休息。全部组完成及已保存会话保留其合法旧动作引用；已保存历史不改组记录、顺序或时长。此规则只用于 v1 迁移，v2 恢复按稳定 ID 验证，不能用原始顺序覆盖新排序。
3. 对已完成组按旧完成时间及 ID 在各会话内回填完成序号，未完成组为 null；新完成事件使用递增序号。迁移事务失败保留原库，提供可报告错误，不做自动丢弃。
4. 更新模型、仓库、界面及 fixture，再用覆盖安装验证旧会话继续、原历史可读及新顺序重启恢复。同步 `lib/core/database/README.md` 和项目 README。
5. 先完成数据库/仓库/Widget 回归，再完成 Android 浅深主题和排序交互验收。回退通过保留 v2 读写能力、禁用换序入口的修复版本完成，不恢复原始数据库快照覆盖用户的新训练。
