# Design

## Context

动机和产品范围见 [proposal.md](proposal.md)，可验证行为见 [app-diagnostics](specs/app-diagnostics/spec.md)、[app-experience](specs/app-experience/spec.md) 和 [data-backup](specs/data-backup/spec.md)。本文件定义新增技术方案，不表示应用已实现。

当前代码为 Flutter／Dart Android 应用，`pubspec.yaml` 为 `0.2.4+10`，业务 SQLite 为 v6，完整备份格式为1。已有仓储事务、`DataWriteCoordinator` 数据集 epoch、备份持久操作阶段，以及无需 Flutter 引擎的原生提醒接收器。诊断应观察这些事实，不能建立第二套业务提交依据。

已确认设计以 [docs/design 入口](../../../docs/design/README.md)、[主规范 §14](../../../docs/design/SetTrace_UI_Design_System_and_Flutter_Spec.md)、[诊断 UI 规范](../../../docs/design/diagnostics/ui-spec.md) 和 [实现对接](../../../docs/design/diagnostics/implementation-handoff.md) 为准：基线 `focus-a-2026-10-14`，增量 `diagnostics-ui-2026-10-23`。采用最新完整设置长图，其他已确认诊断页面保持。

已观察的接入边界及本提案的变化：

| 当前实现 | 计划接入与限制 |
| --- | --- |
| `lib/main.dart` 在 `runApp` 前打开数据库，没有独立启动故障界面 | 提前初始化轻量诊断与错误处理；失败时呈现不依赖业务仓储的 L07 |
| `WorkoutRepository._committed` 在事务后重新读取，并调用 `onChanged` | 在真实事务返回处确认提交；读取、提醒、刷新另记结果，不能按整段方法是否抛错判断回滚 |
| 备份协调器已有 `core_committed`、`settings_pending` 和中断核查 | 复用真实持久阶段及 epoch，只增加观察，不重放、不更改恢复资格 |
| `RestAlertsStore.claim` 在同一事务判断多项条件，多条拒绝路径返回空 | 增加与同一次判断一致的诊断原因，不另查旧状态猜原因，不改变领取结果 |
| 提醒接收器 `goAsync` 后在原生执行器工作，无 Flutter 引擎 | 原生可直接记录，日志不依赖 Activity、MethodChannel 或业务页面 |
| 设置数据分区目前受 `onBackup != null` 控制 | 独立控制两条入口可用性，诊断不随备份回调缺失而消失 |
| `PlanFilesBridge`／`BackupFilesBridge` 已有下载目录写入和核验模式 | 借鉴发布与清理机制；诊断另有预算和任务，不复用2 MiB计划上限、64 MiB备份上限或活动训练拦截 |
| 首次说明 `currentNoticeVersion = 2` | 提升到3，补充本机诊断；保留真实已阅持久化与展示队列 |

既有 `app-experience` 的“发布行为支持本地隐私说明”未区分业务数据与新增诊断文件的备份范围。本提案在该 requirement 及“系统备份与迁移遵循用户系统设置”场景中明确区分：业务系统备份／迁移不额外全局禁用，新增诊断独立排除。其余原有场景保留；这是与已确认诊断隐私设计衔接的显式规格澄清，不通过修改全局备份开关实现。

## Goals / Non-Goals

**Goals:**

- 任一主要失败能关联操作、真实业务提交、后续平台动作、已知降级和恢复；证据不足时明确未知。
- Dart 与后台 Kotlin 使用同一字段契约和隐私边界，业务路径只承担有界入队；磁盘、内存、临时文件均有硬上限。
- 用户可核实地获得诊断 ZIP；失败、局部缺失、取消及发布结果未知是独立结果。
- 启动数据库故障、记录关闭、无操作日志和受限存储均有可用出口及真实 UI 状态。

**Non-Goals:**

- 不更改业务数据库、计划／训练／历史含义、提醒竞争和备份格式；不以日志恢复或重放业务。
- 不捕获每次绘制、输入和 SQL；不做应用内原始日志浏览器、远程收集、自动分享或上传。
- 不承诺强杀、OOM、断电、ANR 或原生崩溃时完整落盘，不为诊断新增常驻服务、唤醒锁或周期任务。

## Decisions

### 1. 使用独立原生写入器，Dart 通过有界接口接入

新增 `lib/core/diagnostics/` 放类型契约、事件目录、非抛错客户端及错误适配；新增 `lib/features/diagnostics/` 放控制器、平台接口和 L 系列页面。Android 新增应用级 `DiagnosticsRuntime`、存储／打包／发布组件及 `settrace/diagnostics` 桥接，具体拆分可依现有命名习惯调整，职责不可混合。

```text
Dart 仓储／服务／错误适配 ── 类型化有界批次 ──> 诊断平台桥接
原生提醒／退出信息／错误适配 ──────────────> 应用级 DiagnosticsRuntime
                                                  │
                                      有界队列 + 串行控制／写入
                                                  │
                                  noBackupFilesDir/diagnostics
                                                  │ 固定截止与分段引用
                                       独立导出工作器（流式ZIP）
                                                  │
                                     Download预发布 → 核验 → 发布
```

当前 Manifest 未声明独立 Android 进程，采用进程内单写入器。通过应用级初始化使接收器先于 Flutter 引擎也可接入；可新增继承现有 Android Application 职责的类，并正确注册，不移除 Flutter 插件初始化。启动入口只提交初始化工作，偏好、文件创建与恢复均在后台执行器进行。策略尚未知时不把缓冲原文写入磁盘；缓冲亦受总预算限制。

记录接口不能向业务抛诊断异常；提供 NoOp 和可注入 fake，使仓储测试、平台不可用和诊断损坏时业务仍可运行。控制／查询／导出接口则返回类型化结果，不能把控制失败吞掉后让界面显示成功。桥接回调只入队，导出不占用日志控制队列执行大文件复制，不持有业务数据库或数据写协调器的长期锁。

选择原因：原生提醒已在无引擎时执行，共用原生写入器可避免两个语言同时改同一日志文件；可在数据库失败时工作。未选仅 Dart 文件日志（漏后台和初始化前失败）、业务 SQLite 日志表（与故障数据源耦合且增加业务写锁）、云端崩溃 SDK（违反离线与无上传边界）。首版使用平台 JSON／ZIP／HMAC 和现有依赖，不引入在线 SDK。

### 2. 字段契约表达顺序、关联和证据等级

事件 schema 首版为1，每条为一行 JSON；事件名、字段名及枚举稳定，中文／英文只用于 UI 和人读摘要。最小公共字段如下：

| 字段组 | 约定 |
| --- | --- |
| 版本与来源 | `schema_version`、实际应用版本／build／构建标识、`event_name`、`module`、`severity`、`origin` |
| 时间与顺序 | 发生时 `time_utc`／时区偏移、接收时 `observed_time_utc`、原时钟单调值／`clock_domain`、进程实例／序号；后台延后观察不得改写发生时刻 |
| 关联 | 随机 `operation_id`、可选 `parent_operation_id`、跨层传递的 `correlation_id`；对象代号含类型和数据集代际；提醒另含修订和轮次 |
| 阶段与结果 | `phase`、`outcome`、白名单 `reason_code`、同一时钟下的持续时间、必要的有限状态变化 |
| 异常与完整性 | `incident_id`、清理后错误类型／指纹；截断、丢弃和不可得原因，禁止自由文本上下文 |

将 Dart 与原生的单调时钟显式标为不同域；只对同域时刻计算耗时。Android 可提供 `elapsedRealtime` 及可验证的开机边界，Dart 自身时钟含进程／isolate 边界。没有可靠映射时用关联 ID、发生／观察时刻与序号说明顺序，不拼接跨重启的精确耗时。

`outcome` 至少区分 `committed`、`rejected`、`cancelled`、`rolled_back_confirmed`、`partial_success`、`unknown`。事务返回后发出提交事实；业务写成功后重新读取失败，单独记录 `followup_failed`，不能覆盖前一提交事实。若提交可能发生但无法确认，优先查询既有业务持久状态，不为日志新增业务账本。缺少结束事件只说明证据缺失。

首版从既有 `backup_state.epoch`／`DataWriteCoordinator` 取得数据集代际。事件携带操作发生时的 epoch，恢复后由已确认提交更新；原生接收器可从本次读取的有效状态获得，无法获得标为未知且禁止据此与另一数据集强关联。加上本机诊断命名空间，避免跨安装或清空后拼接重复数字 ID。

选择原因：沿用结构化日志常见的事件时间／观察时间、关联身份和属性模型，但只保留可解释且获准字段。未选自由拼接字符串或只用异常堆栈，因为无法区分真实事务结果、跨层竞争和用户取消。

### 3. 事件目录围绕主要问题，按业务提交边界记录

在代码旁维护可检查事件目录：每个事件列生产者、级别、必填／可选白名单字段、阶段、是否采样、聚合键和支持的错误码。下面是首版必须覆盖的族，不要求把一个业务动作在每层重复记录。

| 事件族／接入点 | 常规必须保留 | 临时详细模式可补充 | 诊断用途 |
| --- | --- | --- | --- |
| `startup.*`／`main.dart`、数据库及备份启动核查 | 启动阶段、版本／schema、数据库打开／迁移结果、未完成操作核查、初始化降级 | 各阶段有界耗时 | 区分无法打开、迁移失败与后续页面失败 |
| `plan.*`／计划仓储 | 创建／编辑／删除／排序的拒绝、提交与失败；必要数量变化 | 有界阶段耗时和资格检查代码 | 区分未提交、已提交未刷新；不保存名称／重量 |
| `workout.*`／训练仓储 | 开始／恢复、完成组、撤销完成、恢复跳过、跳过剩余组、本次编辑／换序、休息修改、保存／放弃的阶段和结果 | 状态机必要分支和有界持续时间 | 还原训练状态，区分本次快照与计划默认配置 |
| `rest.*`／Dart 服务、原生 Store／Bridge／receiver | 调度策略／截止、领取、有效性拒绝、请求输出、下一轮、确认／取消、失败与降级 | 重复轮次有界明细、平台检查耗时 | 分析没有提醒、重复提醒、延迟和旧回调 |
| `history.*`／历史加载与删除 | 查询失败、删除提交、后续刷新结果和恢复 | 慢查询阶段／次数摘要 | 不把统计读取失败当作删除失败，不导出完整历史 |
| `plan_transfer.*`／计划编解码和文件桥接 | 导入解析／校验／保存，导出构建／复制／发布／核验，取消和权限失败 | 条目数量、字节数和耗时 | 不保存文件内容、来源名称、路径或输入正文 |
| `backup.*`／既有协调器与持久元数据 | 快照、校验、保护副本、核心提交、设置结果、撤回及中断核查的既有真实阶段 | 有界耗时／数量 | 区分核心成功与设置／提醒重建失败，不改变备份资格 |
| `settings.*`、`navigation.*` | 实际偏好提交／失败；通知返回的接受／拒绝与原因；关键恢复路径 | 有限页面枚举转换 | 不记录每次 build／滚动；用户取消不视为错误 |
| `diagnostics.*` | 记录策略、已知丢弃、存储降级、导出阶段／结果与清空边界 | 采集耗时和限流摘要 | 识别日志自身不完整；关闭时不借此持续写操作日志 |

组索引、修订、轮次、数量和必要布尔值按事件最小需要提供，不在每个事件拷贝整个会话。不得增加当前没有的逐组重量／次数、备注或预计时长功能。已有 Picker／跳过资格、结束休息、撤销完成和恢复跳过各自按既有规则命名，不能合并为泛化“撤销”事件。

原生提醒从同一次 `claim` 判断返回有限诊断原因，如旧修订、旧轮次、已确认、超过首次迟到窗口、会话无效、恢复保护；无法细分即 `condition_mismatch`／`unknown`。依然保持首次迟到超过30秒失效、重复不补发和最多一次有效领取。通知／声音请求成功只表示接口已接受，不等于用户看见／听见；权限、通道、精确闹钟、节电能力仅记录实际可读取状态，不推测厂商根因。

选择原因：需要能回答“发生在哪个阶段、是否提交、后面哪一步失败”，而不是最大日志量。未选普遍打印 SQL、所有点击或每次轮询；正常列表重建不产生常规日志，受控慢操作可聚合。

### 4. 隐私在持久化之前执行，详细模式不扩大数据范围

Dart 入口接受类型化字段，原生入队再次按事件 schema 校验。超出白名单的键直接拒绝或删除并计数。禁止调用通用 `log(message, object)`；禁止直接写 `exception.toString()`、Flutter diagnostics tree、SQL 参数、文件异常原文和原始系统跟踪。允许清理后的异常类型、稳定错误代码、受限的库／方法／行号堆栈；路径只允许明确认可的包内相对源码位置。清理器失败则丢弃该字段／事件，不能回退原文，也不能递归记录自身异常。

对象关联使用原生持有的随机密钥做 HMAC-SHA256，输入为命名空间＋对象类型＋数据集 epoch＋内部数字 ID。Dart／原生经同一转换得到代号；原始身份仅在受控内存和进程内平台消息中流转。不同对象类型不共用代号，清空成功后轮换命名空间／密钥。名称、输入、重量和文件正文直接排除，不能通过普通哈希“脱敏”。密钥不出私有控制目录，不进入 ZIP、系统备份或完整备份。

环境白名单只含应用／构建、Android API／系统版本、必要设备型号类别、语言／主题、时区、可读取权限／通道／调度能力、诊断策略和分档存储状态。禁止 Android ID、序列号、账号、广告 ID、任意系统属性枚举、完整安装列表、CPU／内存转储和屏幕内容。现态快照仅包含必要会话状态、有限计数／修订／截止与权限状态，标注各自采集时间，不导出数据库、完整训练列表或通知正文。

仅导出控制 journal 可私下保存本应用创建的目标 content URI／路径，用于核查与清理自己的未交付输出；不接受任意用户来源 URI，不写进事件、异常或 ZIP。L04/L06 可显示本应用生成的实际诊断文件名。

选择原因：文件一旦落盘再做导出脱敏无法保护私有旧日志；白名单比正则穷举敏感模式可验证。ZIP 首版不加密，界面必须说明脱敏局限与主动分享边界，不称完全匿名。

### 5. 有界存储、队列和聚合保证诊断不拖垮业务

根目录选 `context.noBackupFilesDir/diagnostics/`，日志、异常、控制、索引、密钥、journal、staging 全部在其中。避免进入 SharedPreferences 备份或业务备份导出路径。不全局设置 `allowBackup=false`，不改变业务数据系统迁移；按平台实际能力验证诊断排除，不承诺任意厂商迁移行为。

| 资源 | 首版硬边界与策略 |
| --- | --- |
| 常规事件 | 16 MiB，JSONL 分段每段最多1 MiB |
| 异常与关联上下文 | 4 MiB，分段最多512 KiB；与常规合计≤20 MiB，详细记录共用此预算 |
| 单条／堆栈 | 普通事件≤8 KiB；清理后单份堆栈≤32 KiB，作为 incident 单独存储，事件只引用 |
| 辅助持久元数据 | 控制、索引、丢弃计数、journal 连同原子替换临时文件≤1 MiB，固定条目数和字符串长度 |
| 私有导出工作文件 | 一次一个ZIP，所有私有 staging 合计≤24 MiB，不额外复制20 MiB源日志 |
| 内存队列 | Dart128 KiB＋原生512 KiB＋面包屑128 KiB＋跨层在途128 KiB，总队列目标896 KiB，硬上限1 MiB；还限制条目数，超限不无界重试 |

上述是逻辑文件字节预算，文件系统分配块和用户保留的公共 ZIP 不在其中。写前预留，计入未关闭段、孤立临时文件和已固定引用的段；不得等越界后才删除。异常预留不能被普通日志侵占；异常自身亦按4 MiB轮转。索引可重建，但扫描有界、损坏尾行截断到最后有效记录，并记录已知缺口。不可读不等于0字节。

记录时间最多7×24小时，容量先到则更早清理。启动、轮转、策略操作、导出边界执行清理；应用不运行时不唤醒设备。导出按固定截止排除过期记录。同一开机边界使用单调时间计算年龄，跨边界使用墙上时间及持久的最近有效时间锚点；检测回拨和异常跳变。无法证明旧段仍在保留期的歧义段保守排除并清理，说明时间异常，不能通过负年龄无限保留。正常向前跳变可能导致提前清理，报告此局限。

达到32 KiB或有待写时约1秒触发异步批写；生命周期变化和导出前做有界 flush，无待写时不保留周期定时器。首版普通高频重复按60秒窗口聚合，首条保留完整线索，后续保留次数／首末时刻；模块、事件、原因、堆栈指纹和必要状态共同决定聚合键。首次新错误、提交事实和重要状态变化不采样；队列极端拥塞时仍可丢失，但丢失计数必须可见。计数器饱和后标为至少该数，不溢出。

级别约定：INFO 为重要提交／转换，WARN 为可恢复降级，ERROR 为功能失败，FATAL 仅为实际不可恢复错误，DEBUG 只在临时模式。预期校验拒绝／用户取消通常为 INFO 或不记录，不能污染错误统计。详细模式使用单调截止且最长30分钟，进程重启立即失效，不持久恢复旧详细期限；到期在事件入口和查询处检查，不新增后台唤醒。

选择原因：文件分段可在数据库故障时读取并隔离损坏，固定预算便于测量；未选无限压缩归档、按日文件但无总量上限或持续 DEBUG。性能验收目标为指定低配设备 release 普通入队 p95≤1 ms，且无主线程文件 I/O；这是待测门槛，不是本轮测得结果。不能通过阻塞训练“确保日志不丢”。

### 6. 错误与退出信息采用尽力记录和明确能力边界

尽早设置 `FlutterError.onError`、`PlatformDispatcher.instance.onError`，有业务 isolate 时接错误端口，链式保留已有处理／展示语义，返回值不能为了诊断吞掉未处理错误。避免额外 `runZonedGuarded` 造成 Flutter binding zone 不一致或破坏已有 DataWriteCoordinator zone。已捕获业务错误由真正知道阶段的服务记录一次，跨层使用同一 incident 引用，不层层复制堆栈。

原生后台错误进入相同脱敏入口；替换当前 receiver 对原始异常的直接 `Log.w` 输出。JVM 未捕获处理链调用原 handler，不等待日志队列或在主线程同步刷盘；只尽力安排有界最小线索，可能来不及写入。无 native signal handler，不读写原始内存转储。启动完成／结束标记仅用于上下文，缺标记不等于崩溃。

Android API30+ 查询本应用 `ApplicationExitInfo`，按真实 reason 常量记录崩溃／ANR／低内存／用户相关退出／其他或未知及时间。系统文字描述不直接复制。只有平台确实提供、在长度／时间预算内且可做帧级白名单清理的跟踪才生成摘要；否则标为 `unsupported`、`not_available`、`permission_denied`、`truncated` 或 `sanitization_rejected`。API31+可能有原生跟踪也不意味着可以直接导出 tombstone。记录已消费的退出线索身份以防每次启动重复，不保存系统原始内容。

选择原因：平台提供的上次退出信息比“上次没写结束”更可靠，同时应区分缺证据与无问题。未选自建心跳判 ANR 或强制崩溃线程落全量文件。发布构建必须能映射实际构建标识到开发侧符号／R8 mapping；若未启用混淆，记录真实状态，不制造不存在的符号文件。

### 7. 诊断包可离线阅读，摘要只下证据支持的结论

首版ZIP格式独立于业务备份，`format=settrace.diagnostics`、`format_version=1`。建议布局：

```text
manifest.json
summary.txt
environment.json
state.json                 # 可选，含分项采集时刻／不可得原因
events/*.jsonl             # 按实际存在的有效段
incidents/*.jsonl          # 脱敏异常及有界上下文
```

manifest 包含随机报告编号、构建、生成时间与固定截止、真实可读覆盖和缺口、策略／schema／能力、各非manifest条目的字节数和SHA-256、丢弃／截断／不可得／不支持原因。manifest 不自包含自己的哈希；整个ZIP的大小和哈希由发布核验结果及私有journal记录。摘要、环境和清单各自有小型上限，共同保证24 MiB staging预算；输出流超过上限立即失败并清理半成品。

摘要列最近关键失败链、最后可确认提交、后续失败和诊断限制，例如“组完成已提交；提醒调度权限受限”“删除已提交；刷新读取失败”。每项引用事件／操作和时间，事实、候选解释、未知分开。只按确定规则生成，不内置在线模型或把相关当根因。条目校验和用于完整性检查，不保证来源真实性或加密。

环境为必要内容，业务状态为可选。没有操作日志仍可生成环境包，范围为“无操作日志”；可选文件损坏但包有效走L06。所有必要内容都不可得或ZIP无法构建走LE01。环境快照和业务快照分别记录时间，不承诺它们与固定事件截止是同一原子快照。发布完成发生在截止之后，其最终结果写入后续本机日志，不能声称已被包含在当前封口ZIP内。

选择原因：同时提供人读摘要和结构化证据，方便用户支持与后续分析；未选纯文本大文件或导出 SQLite，因为前者无法核验结构，后者泄露完整业务数据且与备份混淆。

### 8. 导出采用单任务、固定范围和真实发布状态机

导出不依赖完整备份协调器，不受活动训练限制。一次只允许一个任务，UI状态绑定 `export_id`／请求代际／来路，重复按钮、页面恢复和旧Future均不能创建第二份文件。

```text
idle → collecting → packaging → writing_unpublished → verifying → publishing
          │              │               │                            │
          └──────── 可取消 → cancelling → cancelled                     └→ published_verified
任一未提交失败 → failed；发布结果不明 → unknown → inspect（不自动重导出）
published_verified + 可选信息缺失 → saved_partial（L06），否则 saved（L04）
```

1. L02主动保存后建立截止和有界flush barrier，超时明确记录未刷入缺口。封闭当前段，持有符合保留规则的段引用。固定收集／打包源引用最长30秒，超时释放并失败／按已可用内容确定缺失，不无限保留旧段。
2. 从固定段和有时间戳的只读状态生成ZIP，使用原生流式输入／`ZipOutputStream`，不一次把ZIP或全部日志跨MethodChannel。导出期间继续业务写入，固定引用计入20 MiB总量；容量不足时先清理未固定最旧段，再丢弃新低优先事件并计数，不能越界。任何时刻都不锁住业务事务等待导出。
3. 本机ZIP关闭后校验条目、大小和哈希，再创建公共待发布目标。文件名为 `SetTrace-diagnostics-<本地时间>-<短报告编号>.zip`；重名生成新名字，实际返回名以平台为准，不能覆盖旧文件。
4. API29+使用 `MediaStore.Downloads` 和 `IS_PENDING`；API28及以下沿用受限旧写入权限，在Download创建本任务专属未交付文件并以不覆盖方式发布。旧版本权限拒绝、永久拒绝与存储错误分别返回，不新增全盘权限。现代媒体API不额外请求旧存储权限。
5. 先持久化本任务标识及本应用拥有的目标定位信息，再写入、关闭、重新读取校验。短发布临界阶段显示“正在完成文件保存…”，不再承诺可取消。发布后再核查可见性／大小／哈希；确认才返回实际文件名、位置和大小。
6. 可取消阶段的系统返回和按钮走同一通道，检查复制取消令牌，清理本任务未发布目标和staging；取消与发布竞争由原生状态机裁决。已发布交付文件绝不在取消清理中删除。清理失败说明残留或未知，不能假报取消完成且无残留。

导出journal在≤1 MiB元数据预算中保留当前任务和有限最近核查记录，例如最多8项，其他已完成项只保留无定位信息的简要历史。处理崩溃窗口：预发布文件创建后尚未记账时按本任务唯一所有权标记发现孤立项；发布后尚未记账时核查原目标，不能根据旧页面阶段重新创建。若可证明未交付，仅清理本任务；若可证明已交付，恢复真实结果；权限或外部修改使结果无法确定则 `unknown`，提供重新核查和手动检查。不能在不确定时删除公共文件或盲目重试生成。

核查不依赖业务数据库，重启不自动重导出。用户后来移动／删除已交付文件时，“上次保存”仍为历史事实，UI不保证文件一直存在。应用正常退出后保留待核查信息；不启动额外后台服务保活导出。

选择原因：平台调用成功和MethodChannel返回均不是完整文件交付证明；已有文件桥接可借鉴但应保持诊断独立。未选直接写最终公开文件后立即显示成功，也不把发布不明当作普通重试。

### 9. 控制操作可核实，清空建立代际边界

原生原子控制文件保存已确认总开关、格式／控制版本、清空代际和密钥；临时详细模式有效期仅驻留当前进程。首次确无控制文件才默认开启；已有文件损坏或不可读时fail closed，暂停新持久记录并显示受限。写入采用有界临时文件与原子替换，空间不足等返回失败，原有效值保持。

关闭成功的线性化点在原生控制队列：先提交关闭策略，停止详细模式，拒绝后续新记录，并清理尚未持久化的对应队列；已开始的写入在确认返回前结束。Dart接到真实结果才更新UI，原生接收器服从同一策略。关闭时仍可读取／清理旧日志、生成用户主动请求的环境包及维护最小控制journal，不借此继续记录用户操作经过。再次开启只恢复常规模式。

清空与导出互斥：仍有导出持有旧内容时要求先完成或取消，不悄悄关闭任务。确认后切换记录代际，使所有旧Dart批次、原生队列和incident引用不可再写回；标记清空意图、删除旧文件并核验，成功后轮换密钥／命名空间并刷新概况。若崩溃或部分删除失败，重启继续识别旧代际并显示真实残留，不将它作为新代际可导出的正常日志。保留用户总开关，不清空公共诊断ZIP、训练、历史或备份；新代际可按当前策略继续记录，因此成功后不保证字节长期为零。

选择原因：只删除磁盘文件会让排队事件重新出现；只重置偏好会让关闭用户被重新启用。未选全目录无条件删除或把公共Download当作本机清空范围。

### 10. 启动故障外壳和已确认UI接入现有职责

启动顺序为 Flutter binding → 轻量错误适配／诊断连接 → 尽力读取主题和语言／初始化格式 → 业务数据库与既有协调器初始化 → 正常应用。业务失败时进入独立可本地化的 `BootstrapFailureShell`，使用相同主题组件，不要求计划／训练仓储可用。主题或语言偏好也不可读时采用现有系统／默认回退，标注可用能力；诊断本身失败不让原本可用的业务启动变为失败。

L07的重试串行执行完整初始化，清理确实已打开的部分句柄，沿原数据库打开规则重试，不删库或建立空库冒充恢复。已有诊断导出经同一原生能力完成，`origin=startup_failure` 保证L04/L06／错误返回L07；正常初始化确实完成后才进入主应用，通知导航仍受既有资格检查。

### 11. 验证以故障链、隐私和资源上限为主线

测试分为 Dart类型／控制器／Widget、Kotlin单元、Android平台集成和人工真机。利用现有仓储／备份／提醒 fake和测试，加入可控时钟、随机源、文件系统、发布器及失败注入点，不依赖真实系统异常随机出现。

- 链路：组完成已提交＋提醒失败、删除已提交＋刷新失败、备份核心提交＋设置失败、通知旧修订／竞争领取、恢复后数字ID复用、数据库打不开仍导出。每条核对事实、关联、UI恢复和业务未重放。
- 隐私：在计划／动作名、导入正文、路径、文件名、SQL参数、通知正文和异常消息注入可搜索哨兵；检查私有日志、incident、摘要和ZIP均无原文，密钥／journal不进包。未列入白名单字段直接拒绝。
- 存储与并发：超过7天／20 MiB、密集异常、队列溢出、时间回拨／跨重启、尾行损坏、索引丢失、只读／低磁盘、固定段容量压力、清空与旧批次／导出竞争，核对所有硬预算和已知缺口。
- 发布：在创建待发布目标、journal记账、复制、核验、发布、返回之间逐点中断；覆盖重复点击、取消竞态、重名、公开文件被移动、无法核查，无重复交付／误删旧文件。
- 平台：API28旧权限、API29 MediaStore、API30退出信息、API31+可选跟踪及当前目标API；运行无Flutter引擎提醒接收器测试。可共用设备合并兼容分支，缺设备不标通过；模拟器不能替代真实听感／厂商系统迁移结论。
- 回归：既有训练／计划传输／历史／备份／提醒／两语主题测试；release合并Manifest无INTERNET／上传SDK／新广泛权限，构建符号对应；StrictMode／trace确认无主线程日志I/O，量测入队与资源预算。

所有开发命令显式工作目录。使用 `D:\ProgramData\Android_SDK`、`D:\ProgramData\Android_AVD`；Android用户目录及工具缓存采用 `D:\ProgramData\DevCache` 下独立目录；TEMP/TMP使用 `D:\ProgramData\DevTemp\add-local-diagnostics`。构建／安装／下载／创建设备前核实实际SDK、AVD磁盘、Gradle／Pub缓存和TEMP配置，缺失／不可写／冲突即说明，不回退C盘。现有 `android/local.properties` 已指向D盘SDK及Flutter；旧脚本的任务TEMP需调整后再用，不引用不存在的开发文档。测试中的 `Directory.systemTemp` 必须继承D盘TEMP/TMP。

实施证据建议位于项目 `docs/qa/local-diagnostics/`，验收记录为 `docs/qa/local-diagnostics-acceptance.md`，记录构建／API／设备／操作／真实结果，区分自动化、模拟器、真机和未验。规划阶段不安装、构建或创建模拟器，不改写既有验收结果。

### 12. 采用可复核的成熟实践，避免引入超出需求的平台

参考 [Flutter 错误处理](https://docs.flutter.dev/testing/errors)、[Android 退出信息](https://developer.android.com/reference/android/app/ApplicationExitInfo)、[Android 共享媒体存储](https://developer.android.com/training/data-storage/shared/media)、[OpenTelemetry 日志数据模型](https://opentelemetry.io/docs/specs/otel/logs/data-model/)。采用结构化事件、关联上下文、有界缓冲、写入前脱敏、用户主动导出和事实／未知分开等方法；无需引入其完整SDK、收集器、网络上传或远程分析服务。

## Risks / Trade-offs

- [默认开启会保留使用时间和必要行为线索] → 说明版本3、开关／清空、字段白名单、七天／20 MiB双上限及无自动发送；详细模式不增加敏感字段。
- [跨Dart／原生契约和后台入口增加复杂度] → 单写入器、版本化事件目录、原生二次验证、无引擎接收器及契约测试；未知字段不原样透传。
- [异步记录可能丢失最后若干事件，强杀／OOM不可完整捕获] → 小批量、关键阶段、平台退出信息和明确缺口；不阻塞业务或承诺完整。
- [存储满、导出固定段与异常风暴竞争] → 写前预算、异常预留、短固定窗口、聚合和可观测丢弃；必要时诊断受限，业务继续。
- [时间回拨或开机边界不可验证] → 独立时钟域和保守保留判定，宁可缺失并说明，不虚构顺序或无限保存。
- [发布与记账之间退出、公开文件被外部修改] → 私有有界journal、所有权核查、未知结果先核查；不自动重导出或删除可能已交付文件。
- [脱敏代码或堆栈来源不受控] → 白名单／拒绝优先、哨兵扫描、稳定错误代码；原始系统跟踪不可直接导出。
- [不同Android／厂商能力不一致] → API守卫、真实能力字段、局部缺失、实测范围报告；保留既有真机待验项。
- [日志与业务事实暂时不一致] → 业务持久状态为准，区分提交与后续失败；日志永不驱动重放或推断数据完好。

## Migration Plan

1. 实施前确认本提案、规格增量和任务一致，并读取当前 `docs/design`。先建立独立运行时及版本1诊断格式，再按业务边界接入，最后连接UI、说明版本3及故障外壳。
2. 不执行业务SQLite迁移，不改变v6或备份格式1。诊断文件首次独立初始化；原业务备份导出／恢复白名单保持，新增诊断内容不加入其范围。验证业务系统备份行为未被全局禁用。
3. 已读版本2的用户按既有真实已阅规则展示一次版本3；恢复业务备份不改变本机诊断控制、密钥、清空代际或详细期限。重启关闭临时模式。
4. 诊断schema未知或损坏时不盲读、不导出原字节；报告不支持／损坏，仍受预算和过期清理。控制版本不支持时暂停记录而非重置为开启。已交付公共ZIP始终由用户管理。
5. 回退应用版本不回退业务数据库；旧版可忽略独立诊断目录。回退版本若不具备诊断清理器，不能承诺继续执行七天清理，应在回退前停用并清空私有诊断或明确残留；禁止以回退为由删除业务或公共文件。
6. 通过所列验证并记录未验边界后才进入后续同步／归档／发布流程。本次只交付规划，不执行实现、主规格同步、归档、Git提交或发布。
