# Design

已检查的现状及其影响：

| 现有位置 | 观察 | 对设计的约束 |
| --- | --- | --- |
| `lib/core/database/app_database.dart` | SQLite v4；计划、会话、动作、组、跳过批次及提醒表；级联与状态触发器 | 采用逻辑数据恢复，保留外键与状态约束；不能直接覆盖数据库文件 |

| `lib/main.dart`、`app.dart` | 启动立即创建仓储并安排提醒／导航 | 插入未决操作检查，先确定数据集，再放行正常写入及呈现 |

`lib/core/database/README.md` 标题仍为 v3，但末节与代码已到 v4；实施时修正标题，不据旧标题设计降级。当前应用 `0.2.4+10` 和原型中的版本／数量均不决定备份兼容。

UI 的主依据按顺序是 [设计入口](../../../../docs/design/README.md)、[主规范](../../../../docs/design/SetTrace_UI_Design_System_and_Flutter_Spec.md)、[页面状态](../../../../docs/design/screens-and-states.md)、[交互](../../../../docs/design/interaction-spec.md)、[验收](../../../../docs/design/acceptance-checklist.md)，加上 [备份 UI 草案](../../../../docs/design/backup/backup-ui-spec.md)。复用 `focus-a-2026-10-14` 及当前四主题色；HTML 和 PNG 仅作画面对照。

## Goals / Non-Goals

**Goals:**

- 将文件版本、应用版本与数据库版本解耦；格式变迁可测试、旧文件长期可读。
- 在外部文件系统、SQLite、SharedPreferences 无共同事务的条件下，保证核心替换原子、保护先完成、结果能在冷启动核实。
- 使普通页面、排队写入、设置保存与原生提醒不能绕过保护流程；失败能说明发生到哪个阶段。
- 让 B/E 设计状态对应真实操作结果，复用已有导航、视觉、双语与辅助输入设施。

**Non-Goals:**

- 不改计划／历史的业务含义，不增加逐组重量、次数、备注、预计时长或新训练状态。
- 不用备份实现同步、增量合并或全局实体 UUID 改造，不导出原生调度与系统授权。
- 不支持导入原始 `.db` 文件、只恢复部分历史、全文剪贴板备份、加密密码或自定义网盘流程。
- 不保证降级旧二进制可打开新数据库；回滚必须使用仍能读 v6 的修复构建。

## Decisions

### 1. 采用独立的逻辑 JSON 格式

选择 `settrace.user-backup` v1，而非复制 SQLite 文件或扩展 `settrace.training-plans`。SQLite 文件会绑定表结构、WAL 和设备状态；计划格式故意不携带历史及身份关系，混用会破坏既有接收者的预期。

拟新增 `docs/user-backup-format.md`，发布前固定下述协议并保存黄金样本。外层结构：

| 字段 | 契约 |
| --- | --- |
| `format` / `schemaVersion` | 固定标识／初始整数 1；决定解析与转换分支 |
| `backupId` | 文件快照身份；不作为实体同步身份 |
| `snapshotAt` / `exportedAt` | UTC ISO 8601，分别为快照生成与本次对外导出时刻；副本再导出保留原 snapshotAt |
| `sourceAppVersion` | 实际来源安装版本及构建信息，仅供详情展示，不作兼容门槛 |
| `data` | `plans`、`workouts`、`settings`，前两者允许为空数组 |
| `metadata.extensions` | 唯一可忽略的非业务扩展空间；不能存必须保留的业务字段 |
| `integrity` | `algorithm: sha256` 与摘要；对排除 integrity 后整个文档的 RFC 8785 规范化 UTF-8 计算 |

拒绝重复 JSON 键、非有限数、非法 Unicode、非安全整数、深度超过 32 的内容和未知业务字段。时间数值使用现有 UTC epoch 毫秒，时长／休息整数秒、重量 kg；`startedLocalDate` 单独存原始 `YYYY-MM-DD`，不从时间戳重新生成。摘要可检测损坏，不是加密或来源认证；文件包含个人记录的事实在 B02 和数据说明可见。

数据是领域对象而非 `SELECT *` 的表转储：

| 对象 | 必须保真的内容 |
| --- | --- |
| 计划 | 文件内 `key`、name、createdAt、updatedAt、按列表顺序的计划；包含有序动作 |
| 计划动作 | 文件内 key、name、targetSets、两类休息、可空 defaultWeightKg；空动作计划合法 |
| 已保存训练 | key、可空 sourcePlanKey、planNameSnapshot、startedAt、startedLocalDate、endedAt、durationSeconds、有序动作快照；仅已保存状态 |
| 历史动作 | key、可空 sourceExerciseKey、nameSnapshot、目标组数、两类休息、可空重量、有序 sets 与 skipBatches |
| 组 | setNumber、可空 completedAt／completedSequence、可空 skippedAt／skipBatchKey；数量与目标一致，状态互斥 |
| 跳过批次 | key、createdAt、可空 undoneAt；所属训练及动作由嵌套结构确定；保留已有批次事实，不生成历史撤销入口 |
| 设置 | themeMode、themeColor、languageTag，以及 reminder.enabled/sound/vibration/repeat/interval |

文件 `key` 是局部引用，允许从本地 ID 确定性生成；不跨文件合并。恢复为每个实体分配新的本地 ID，按映射恢复来源关系、完成顺序、跳过批次与数组顺序，保留原用户时间及名称。数据库 AUTOINCREMENT 高水位不重置，避免旧页面／通知 ID 与新对象复用；现有对象 ID 不被写入外部 API 承诺。来源计划／动作已删除时允许 null；存在的来源引用必须指向文件内正确对象，不能指向目标设备残存对象。

历史字段按该格式版本可表达的保存语义验证，不借恢复自动 trim、截断、重命名或套用未来更严格的编辑范围。已保存时长以存值为准：现有保存采用 `max(0, ended-started)`，系统时钟曾调整时不能仅因起止倒序重算时长或丢记录。首版无 v0 完整备份；计划文件 v1 不是完整备份的旧版。

### 2. 兼容性采用单向转换和发布样本门槛

建立 `BackupCodec`／版本转换注册表：识别 → 按原版本验证摘要与结构 → 纯转换 → 当前语义验证 → 待恢复模型。转换在候选暂存区进行，原文件不变，直到全部通过才生成 B06。旧格式转换中的缺省值必须在版本映射表说明；只为后来新增且无历史事实的字段补默认，不能把未知组状态推断成跳过。

| 情况 | 处理 |
| --- | --- |
| 同一格式、不同应用补丁／数据库内部版本 | 接受并按完整规则验证 |
| 已发布旧完整格式 | 顺序转换至当前模型，不要求中间安装 |
| 高于支持版本 | E01 更新应用／重新选择；不猜测当前最低版本、不自动打开网络 |
| 当前格式含未知业务字段／枚举 | 拒绝；新业务字段应升级格式，不能通过忽略字段制造有损成功 |
| 扩展元数据新增 | 保留摘要验证，允许不参与业务恢复 |
| 旧保护副本 | 使用同一版本读取器，升级不删除旧文件 |

首版测试 v1 黄金文件、未来版本拒绝与合成升级管线；不能把测试用 v2 当成已发布格式。以后每次格式升级必须保留全部已发布版本样本并验证其最终数据和统计。数据库 v5/v6 的本地升级与 JSON v1 读入完全是两套迁移。

### 3. 容量和 Android 通道独立于计划分享

完整文件 v1 原始 UTF-8 上限定为 64 MiB（包含空白、BOM、元数据），读写同限；这是本次新增的容量契约，不来自 UI 中的 186 KB 示例。十年每日一场、每场 8 动作×5 组的基准夹具和接近上限夹具必须验证。超限时说明当前支持容量且无损停止，不自动截断或要求删历史；当前数据过大导致保护副本无法创建也必须停止恢复。

新增 `BackupFilesPlatform` 与 `BackupFilesBridge.kt`，使用系统 ACTION_OPEN_DOCUMENT，后台流复制至应用暂存文件，逐块计数及核验；MethodChannel 仅传请求 ID、可信内部文件令牌、文件名、大小及结果，不传整份 JSON 或接受任意路径。Dart 解析／规范化在工作 isolate，按版本限定嵌套和条目结构，临时文件流读写，避免 UI 主线程处理大文件。性能夹具必须记录时间与峰值内存；若一次 JSON 解码峰值不达设备门槛，改为增量解析至暂存模型而不能缩小既定兼容上限。

Android 29+ 复用 MediaStore 的 pending 发布模式，写入、关闭、重读摘要通过才发布成功；旧支持系统使用唯一目标与临时文件、flush/fsync、重读后完成，并处理需要的存储权限。只有真实完成才返回 success；取消与稳定错误类别分开。清理失败不能把残缺输出称为成功，保留本次 URI／令牌作幂等清理重试，绝不删除已有备份。完整备份桥接与旧 PlanFilesBridge 共享文件选择互斥，分别保留各自格式和大小规则。

选择文件后将固定字节保留在私有暂存候选中；预览显示的是这个快照，外部 URI 后来被修改不会静默改变已选择内容。确认再次核验内部候选摘要；候选被替换、丢失或读取失败则失效。取消、重新选择和超时清理不能遗留可提交旧候选。暂存区可清理，保护副本区不能作为缓存清理。

### 4. 数据快照与操作门闩覆盖真实写入

新增应用级 `BackupCoordinator` 和共享数据操作协调器，注入计划、训练、提醒偏好及外观／语言写入入口。普通操作保持原语义，在进入写入时检查数据集 epoch；恢复进入独占阶段后拒绝新的冲突写入，排队的旧意图在释放后也必须核对 epoch，不能延后作用于新数据。

快照流程等待已发起的语言／明暗保存、`ThemeColorController.settled` 和提醒偏好保存，读取成功确认值；失败的临时预览不进文件。协调范围内从一个 SQLite 一致读事务取计划和已保存历史，同时读取被冻结的已确认偏好，核实无活动会话。快照固定后普通导出可释放门闩，后续编辑不会改变本次文件。恢复确认后门闩保持到保护与核心提交结束。

门闩先停止接受新冲突意图，再排空已获准的在途写入，最后获得快照／替换独占权；不得持有这些在途操作尚需获取的同一锁再等待 settled。普通设置操作保留原来的非阻塞导航行为，只有实际快照／恢复临界区限制冲突写入。

预览令牌包括候选摘要、当前语义内容摘要、设置选择、数据集 epoch、操作 ID。确认持有门闩重读摘要和活动会话；任何差异进入 E08／B15。内容摘要基于归一化的领域数据，局部引用按稳定遍历重新编号，排除文件 ID、导出时刻和备份管理元数据，包含用户名称／时间／顺序／组状态及可迁移设置。不能用记录数量、最大时间戳或 UI 是否重建判断新鲜程度。

分别计算 coreDigest（仅计划和历史）与 settingsDigest，再组合成预览／导出内容摘要；核心事务内只用目标 coreDigest 核验业务替换，不能因尚未应用的设置不同误判失败。设置摘要只在对应阶段核验。候选完整性摘要与上述语义摘要用途不同，前者核验文件字节的规范化内容，后者核验数据是否改变。

当前导出成功时保存「导出时刻＋该快照摘要＋实际文件信息」，首页重新比较当前语义摘要。可用应用内 revision 缓存计算，但冷启动和提交前必须读取真实数据。当前状态不可读时显示未知；保护副本导出不改本机当前导出标记。若文件已成功但导出状态记账失败，结果保留实际文件成功事实并提示状态未更新，可仅重试记账，不重复生成文件；启动通过本次导出请求记录核实后修复。

导出记录在公共写入前保存请求 ID、快照摘要和预留目标 URI／路径，平台发布回执可对账。重启仅对该请求拥有的目标重读验证：完整且已发布则补记，明确未完成则清理；无法读取则显示待核实，既不宣告成功也不删除可能已完成的公共文件。成功文件的清理权限不因应用状态记账失败而扩大。

替代方案是只禁用页面按钮；该方案挡不住旧请求、主题色队列及原生回调，因此不能作为一致性保证。原生接收器只操作提醒表，但仍需在 v5 未决核心阶段拒绝输出／导航；提交后的无活动会话校验和不重置 ID 高水位共同防止残留意图重新生效。

### 5. v5 控制元数据与 v6 顺序持久化，核心替换保持单事务

在 `AppDatabase` 追加 v4→v5，不修改现有业务列和历史事实，增加：

- `backup_operations`：操作 ID、类型（export/restore/undo）、阶段、候选与原状态摘要、保护副本 ID、设置选项、待恢复设置及逐项结果、原 epoch／目标 epoch、关联被撤回操作、失败分类和时间。核心提交标记与业务替换必须在同一 SQLite 事务。
- `backup_copies`：副本 ID、生成操作、快照时刻、可信相对路径、摘要、格式版本、核验数量、状态（ready/deleting/missing）。不对业务记录使用级联删除关系。
- `backup_state` 单行：当前 epoch、上次当前数据导出信息、最近可撤回操作等控制状态。副本和操作历史不进入备份载荷，不随核心替换删除。

保护副本存 Android 应用 files 下的专用持久目录 `backup-recovery`。先写同目录临时文件，flush/fsync，原子改名，重新读入并完整校验，再登记 ready。只有 ready 且内容吻合当前快照才能替换。注册前中断留下的完整文件按受控命名及摘要扫描登记为孤立保护副本，不静默删除；未完成临时文件可清理。文件路径不得来自外部 JSON。

核心事务内再次检查 epoch／无活动会话／当前摘要，按外键依赖清除旧业务数据与旧提醒，写入所有目标计划、已保存会话、动作、批次和组，恢复引用，核验计数、外键及语义摘要，增加 epoch，并写 core_committed。清除组／批次时按依赖次序处理，不能关闭外键或触发器来容忍损坏。训练游标等内部派生字段按已保存状态生成，所有旧休息及 current_rest_alert_id 为空；不导入 rest_alerts。

任何异常回滚整个事务；只有事务回滚后重读旧摘要吻合，才能进入 E07/E13。事务结果未知或 DB 无法打开时进入 B16 检查失败，不使用保护副本自动覆盖一个可能已提交的新状态。文件交换方案需要处理活连接及 WAL，且更难与原生提醒协调，因此不采用。

### 6. 明确跨存储设置恢复阶段

核心事务不修改可迁移设置；取消勾选时全部保留。勾选时在核心已提交后进入 settings_pending：提醒偏好作为一个 SQLite 子事务组保存（保留 permission_requested）；明暗、主题色、语言分别保存，成功后才更新对应运行状态。主题色恢复走受协调的提交路径，清除失效的旧预览／失败目标，不能直接写 prefs 而遗漏控制器确认缓存。

持久日志记录每项目标、原确认值和结果。SharedPreferences 无共同事务：若写成功但日志更新前进程退出，启动重读并对比目标，幂等补记；读失败保留 pending，不伪报。所有写入路径在同一门闩下；用户后续明确修改某项时，先持久取消该项旧重试意图再应用新选择，新恢复取消旧操作全部残留重试。记录不成功则不发起会让旧意图失控的新设置写入，并显示当前设置保存失败。

E09 显示已经成功的核心及具体未恢复设置，提供「重试恢复设置」「使用当前设置继续」；后者将剩余意图终止，保留实际已成功值，不偷偷回滚成功设置。未处理提示在首页仍可找到。恢复任务发生过设置失败时不自动无限重试。B16 冷启动先重读／补记已实际完成的项，剩余项交 E09 用户处理。

所有设置尝试成功后才显示完整完成；E10 刷新失败只加载数据。多种问题同时出现时核心结果始终明确，优先展示设置待处理并保留刷新问题，解决后再重读；不能因一项失败重跑核心。

### 7. 持久状态机与启动协调

恢复／撤回的阶段及重启判据：

| 阶段 | 持久事实 | 重启动作 |
| --- | --- | --- |
| validating / preview | 当前业务未变；候选仅供检查 | 可丢弃候选回 B05；不自动确认 |
| preparing | 操作和原摘要已登记，保护可能尚未 ready | 核实原数据；清理未完成暂存；保留完整孤立保护文件 |
| protected | 保护文件已验证并登记；核心未提交 | 核实旧数据，B17；用户重新预览才可再做 |
| applying | 只在内存表达，事务外没有“已成功”标记 | SQLite 恢复事务后依据 committed 标记判断；不凭动画阶段判断 |
| core_committed / settings_pending | 业务与 epoch 已同事务提交 | 核验新状态；补记已写设置或 E09，不重放核心 |
| completed / settings_skipped | 核心和设置处理结果明确 | B18 或 B14；只刷新，E10 不重写 |
| indeterminate | 无法读取／核实持久事实 | B16 检查失败＋重试，保留文件；不放行数据写入 |

核实未提交且原数据完整后将操作记为 aborted，正常恢复写入；结果提示按已展示状态管理，不每次启动重弹。已提交状态以同事务标记为事实依据，提交时已核验 coreDigest；如果 E09 后用户已经合法新增记录，重启检查允许这些后续写入，不能要求当前数据仍等于刚恢复时的摘要、冻结应用或自动回滚。此时检查数据库结构／引用一致性及操作归属，结果摘要与当前数量分别显示；后续恢复产生新 epoch 后旧操作只保留历史结果。

在 `main.dart` 打开数据库和本机偏好后、启动普通仓储导航与提醒呈现前执行恢复检查；需要交互的检查由受限启动页面承接，避免空白页。先确定当前数据集，再初始化有效主题／语言并安排首次说明、通知和权限 UI。原 D15/D11/D17 串行规则保持；B15 有活动训练时正常提醒继续，不因为浏览备份延长截止。真正替换要求无活动会话，旧通知点击在操作完成后重新核验，失效提示不能跳入其他对象。

### 8. 副本管理与撤回绑定具体操作

最近可撤回操作指向其自己的 before-copy；查看其他副本不改变快捷撤回目标。恢复后添加数据不移除撤回入口，但 B11 比较的必须是最新数据，B13 新建并验证保护副本后才替换。

撤回的设置范围采用被撤回操作的原设置选择：原来未恢复设置，撤回保留当前全部设置；原来选中设置，撤回同时恢复 before-copy 的设置，即使原来只成功了一部分。B11/B12 增加明确一行说明，保护副本包含撤回前所有设置以供找回。这是对原型尚未写清的范围补充，不新增复杂选择。

撤回成功后标记原快捷操作已撤回，不自动在同一按钮上切换成“重做”；撤回前新副本可从 B10/B19 明确选择恢复。任意旧副本恢复走普通 B06/B07，设置默认可选。删除指定副本先持久记录 deleting，再删文件，再更新索引；重启完成已授权的同一删除。文件仍在则失败保留可重试；文件已删但索引尚在则按事实修复，不能报告“副本完好”。删除从不自动寻找下一份替代撤回目标。

副本不自动过期；显示数量、大小和卸载边界。低空间停止新的恢复并提供进入副本管理／重新选择的出口，不能后台清理用户尚未确认删除的副本。Android 系统备份配置保持原规则，不承诺系统一定带走或排除这些副本。

## Risks / Trade-offs

- [多次完整副本占用空间] → 不静默清理，提供大小、逐份导出／删除；空间不足停止替换。预检查只是提示，所有实际写入／核验失败仍需处理。
- [64 MiB 解码峰值与旧设备性能] → 流式通道、isolate、有界校验及多年／上限夹具，测量后优化增量解析；不靠隐藏截断满足性能。
- [跨存储无法一次提交] → 核心单事务、逐项设置日志和实际值核验、只重试设置；成功页准确说明范围。
- [进程在文件与数据库交接时退出] → 先持久核验副本、事务内提交标记、启动对账、孤立文件登记和幂等删除；未知时禁止猜测写入。
- [旧导航／主题队列／原生通知晚到] → epoch 与候选摘要、共享门闩、排空偏好队列、旧事件失效；原生 v4/v5/v6兼容和独立故障注入。
- [格式演进误丢数据] → 禁止未知业务字段静默忽略，保留所有已发布样本和完整快照验证；语义版本与数据库版本独立。
- [用户将应用内副本当成卸载保护] → B01/B10/B19/D15/D16 区分存储位置，完整文件为未加密个人记录，不写“已自动同步”。

## Migration Plan

1. 在获授权的 apply 中先固定 JSON v1 字段表和黄金样本，实现转换注册与校验；现有计划格式／历史含义不变。
2. 追加数据库 v5 控制元数据及 v6 顺序字段、原生 v4/v5/v6读取兼容，验证 v1/v2/v3/v4/v5升级、失败回滚及活动训练／提醒语义保留。不在升级中自动导出、恢复或创建全量副本，不清空用户表。
3. 接入文件平台、操作协调、核心替换／设置／副本状态机和启动检查，故障注入通过后再连 UI。
4. 实施 B/E 页面与说明版本2，更新当前设计文字、数据库说明、格式文档；保留之前 UI 草案及 QA 的证据边界。
5. 跑相关存储、平台、UI及既有回归，记录设备、应用构建、格式、数据库版本与限制。发布前完成真实公共文件往返、卸载重装、设备迁移及中断验证；规划阶段不发布或提交代码。
6. 如需撤销该功能，提供仍兼容 v6、保留业务数据与保护文件的修复构建，可暂时禁用新恢复入口但保留读取／导出救援；不安装只读v4的旧构建、不要求卸载、不用过时保护副本自动覆盖新记录。
