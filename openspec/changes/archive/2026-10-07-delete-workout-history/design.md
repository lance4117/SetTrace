# Design

## Context

动机见 `proposal.md`。当前应用为离线 Flutter Android App，使用 sqflite 本地 SQLite。`WorkoutRepository.discard()` 通过 `_activeRow()` 限制为进行中的训练，不能直接用于删除历史；`listHistory()` 只读取 `status = completed`，完整完成和提前保存共用此状态。

数据库已启用 `PRAGMA foreign_keys = ON`，`session_exercises.session_id` 与 `session_sets.session_exercise_id` 均有 `ON DELETE CASCADE`。训练快照到原计划的外键不会反向删除计划。

`HistoryPage` 保存全部历史和所选月份，`HistoryStats.calculate()` 在构建时计算本周、本月、所选月时长/组数和全部历史中的最近训练。当前 `HistoryDetailPage` 为只读 StatelessWidget，列表推入 `MaterialPageRoute<void>` 且不等待详情返回结果。现有测试已使用 sqflite_common_ffi 和可控仓储子类，适合复用测试模式。

本变更跨越仓储写入、详情导航与列表状态，需明确成功与刷新失败的边界，因此创建本设计文档。

## Goals / Non-Goals

**Goals:**
- 以单条历史的稳定 ID 定位，在一笔事务中验证状态并永久清理其关联数据。
- 让导航结果、列表缓存和数据库提交结果一致，统计继续来自记录集合。
- 在异步写入、返回和重新加载时防止重复提交、过期查询覆盖及错误成功反馈。

**Non-Goals:**
- 不新增软删除字段、累计值表、全局状态框架或数据库版本迁移。
- 不修改 `discard()` 的进行中训练语义，不调整现有日期归属、时长或最近训练排序规则。
- 产品范围见 `proposal.md`，不将本次训练删除扩展为计划或文件备份管理。

## Decisions

### 1. 新增独立的历史删除接口

在 `WorkoutRepository` 新增 `Future<void> deleteHistory(int sessionId)`。在事务中读取目标，确认存在且 `status = completed`，再按 ID 和 completed 状态删除 `workout_sessions`，检查删除行数为 1。不存在和进行中的目标分别抛出可被 UI 映射为明确提示的状态错误，任何失败均回滚。

使用现有级联清理动作和全部组记录，不逐表手动删除。拒绝扩展 `discard()`，因为其调用方与确认文案针对进行中的训练；独立接口可直接表达历史删除边界。拒绝软删除，因为本次目标是永久清理数据库且不提供恢复，软删除需要改变查询与模型。

### 2. 在详情页管理确认与异步状态

将详情页改为 StatefulWidget，传入现有 `WorkoutRepository` 和记录快照；保留已有查看内容。右上角更多菜单提供“删除记录”，沿用计划详情的菜单与对话框模式，显示名称快照、本地训练日期，以及“删除后无法恢复，相关训练统计将同步更新”。取消、关闭或返回确认框均不调用仓储。

详情维护覆盖确认和写入阶段的操作状态，避免重复弹窗和重复请求；写入期间禁用删除操作并约束返回，显示进度。失败恢复操作、保留详情，通过可理解的文案允许再次操作，不直接输出内部异常。数据库提交后才 `Navigator.pop(context, true)`；异步完成后检查 mounted。普通返回使用 null/false，不伪报删除成功。

选择详情页入口以便用户核对训练内容，并与现有更多菜单保持一致；列表滑动删除和批量操作留在本次范围之外。

### 3. 按返回结果刷新并保留所选月份

列表等待 `MaterialPageRoute<bool>` 的详情结果，仅成功删除结果触发删除反馈和重载。提交成功后先从本地 sessions 集合移除已删 ID，让 `HistoryStats.calculate()` 即刻从剩余集合重算，再调用 `listHistory()` 获取数据库最新状态；所选 month 不重置。

刷新使用请求代次或等效状态校验，使删除前启动的旧查询不能覆盖删除后的状态。该校验局限在历史页，不引入全局事件系统。当前月份次数仍以 now 的自然月计算；所选历史月份仅决定列表、时长和组数。

若数据库已提交而重载失败，已删 ID 继续从页面排除，提示“记录已删除，刷新失败，请重试”并提供刷新重试，不重新发起删除。目标已不存在时提示实际状态并重新加载列表，不显示“本次删除成功”。不采用独立累计值减法，避免多处维护造成漂移。

### 4. 用实际数据库和导航验证行为

仓储测试覆盖完整/部分保存记录、同日多条精确删除、原计划/其他历史/活动训练保持、目标不存在/活动状态拒绝、关闭重开后仍删除。查询三张记录表确认没有关联残留，并用测试用临时触发器制造级联删除失败，验证事务回滚和外键完整性。

统计测试保留当前日期口径，覆盖删除对周/月次数、所选月时长与组数的影响，最近记录替换和最后一条记录归零。UI 测试复用可控仓储子类以注入延迟、删除失败及删除后刷新失败，检查取消、重试、重复点击、导航返回、月份保留及过期刷新结果。

## Risks / Trade-offs

- [永久删除不可恢复] → 确认框展示训练身份和明确后果；菜单入口避免训练中误触，无撤销承诺。
- [级联配置失效可能留下残留] → 使用 AppDatabase 打开的实际数据库验证两层级联及外键检查，覆盖重开后的删除结果。
- [删除成功但刷新失败造成反馈混淆] → 分离数据库写入与列表刷新结果，先移除本地目标后重载，并允许仅重试刷新。
- [旧查询或异步返回覆盖最新列表] → 历史页刷新代次校验、mounted 校验以及提交期间的操作/返回保护。
- [测试通过但 Android 小屏确认内容被截断] → 在浅深主题、360–430 dp 和放大字体下验证菜单与确认弹窗；内容必要时可滚动。

## Migration Plan

1. 在现有 v2 数据库上添加仓储与 UI 能力，数据库版本、表结构和依赖保持不变，不运行清库或数据转换。
2. 在测试夹具中检查旧版已有的完整/部分保存记录可删除，原计划、其他历史与活动会话可继续使用。
3. 实施时运行 Flutter 分析及相关/全量测试，完成 Android 交互验收后发布。
4. 若需回退应用代码，数据库无需回退；已确认删除的数据不会随版本回退恢复，该限制已在确认框说明。
