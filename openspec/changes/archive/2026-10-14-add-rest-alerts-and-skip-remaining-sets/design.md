# Design

## Context

动机见 `proposal.md`。本项目是 Flutter/Dart、Android 优先、SQLite 离线应用。已核查的集成点：

- `WorkoutPage` 的 `Timer.periodic` 刷新倒计时，恢复时先 `normalizeRest()` 再读取会话，不能承担后台唤醒。
- `WorkoutRepository` 在事务中完成、撤销、调整休息和换序；`_pendingSets()` 当前仅以 `completed_at IS NULL` 判断待练。`updateExercise()` 缩减目标时删除多余组，不能作为跳过实现。
- `SessionExercise.completed` 和 `WorkoutSessionData.allSetsCompleted` 当前通过真实完成数与目标比较；完成提示、下一动作和结束确认共用了这些判断，需要引入独立的待练判断。
- 数据库 v2 有稳定的会话动作 ID、完成序号与绝对休息截止时间；恢复、换序与迁移已有 FFI/Widget 测试。
- 历史详情已显示实际完成/目标比例，但逐组只区分完成时间与未完成；`HistoryStats` 使用实际完成数汇总。
- 设置目前是主题和语言；`SetTraceApp` 保持 Navigator 与根页，`RootTabs.openWorkout()` 是训练导航入口，目前没有通知导航。
- Android 已通过 `MainActivity` 和 `PlanFilesBridge` 使用 MethodChannel；Manifest 尚无通知和精确定时权限。本设计沿用该原生桥接方式，不引入云服务或新的 Flutter 通知插件。
- `fix-workout-timer-recovery` 没有 proposal/design/specs/tasks，不作为本变更依赖。现有主规格要求的计时恢复行为须继续保留。

## Goals / Non-Goals

**Goals:**

- 数据库是完成、跳过、当前休息及提醒消费状态的唯一依据；页面与 Android 到期回调读取同一份有效状态。
- 训练事务可靠提交，提醒是提交后的可重试系统副作用；调度异常不伪装成训练保存失败。
- 在不删除目标组、不伪造完成的条件下推进训练，支持恢复、排序和两种独立撤销。
- 提供可测试的时间、调度、声音与通知边界，避免只用模拟前台计时器证明后台能力。

**Non-Goals:**

- 不改变计划表、计划 JSON v1、完成日期、训练起止时长和逐组记录粒度。
- 不在原生侧重新实现训练动作迁移或组完成事务；原生提醒桥只处理提醒表、读取会话有效性并报告结果。
- 不为手机重启注册恢复广播，不使用持续前台服务，不申请绕过勿扰权限，不新增组开始操作。
- 功能排除项见 proposal；本次只产生规划产物，代码修改留给 apply。

## Decisions

### 1. 为组增加跳过标记与可撤销批次

数据库升级到 v3：为 `session_sets` 增加可空 `skipped_at` 和 `skip_batch_id`；增加 `session_skip_batches`，记录会话 ID、动作 ID、创建时间和撤销时间，以自增批次 ID 作为稳定先后顺序。组只引用自己会话内的动作和批次；批次随会话删除级联清理。具体索引与约束在实现中按查询设置，但必须确保完成与跳过互斥。

组状态派生为：

| 状态 | completed_at | skipped_at | 参与待练 | 参与实际完成统计 |
| --- | --- | --- | --- | --- |
| 待完成 | null | null | 是 | 否 |
| 已完成 | 非空 | null | 否 | 是 |
| 已跳过 | null | 非空 | 否 | 否 |

`completed_sequence` 继续只排序真实完成记录。跳过不分配完成序号。可通过数据库触发器及事务条件更新保护互斥和引用归属；无需重建既有组表来增加状态枚举。

备选方案：直接减少 `target_sets` 或把跳过组填成完成。两者都会破坏用户确认的“2 / 4 组完成”及实际训练量，因此不采用。仅记录动作级提前结束也无法直接在逐组详情区分跳过与未完成，且难以精确撤销。

### 2. 增加待练判断，不改变真实完成口径

- `SessionSet` 增加 `skipped`、`pending`；`SessionExercise` 增加 `pendingSets`、`skippedSets` 和 `resolved`（没有待练组）。保留 `completed` 表示全部真实完成。
- `WorkoutSessionData` 增加 `hasPendingSets`/`readyToFinish`，结束提示使用后者；`allSetsCompleted` 仍表示全部真实完成，不赋予双重含义。
- `_pendingSets()`、`_repairCursor()`、`completeSet()`、`nextExercise` 与恢复全部以 `completed_at IS NULL AND skipped_at IS NULL` 选组。先继续当前动作待练组，否则按保存顺序找第一待练组。
- `completeSet()` 的条件更新必须排除已跳过组；如果只剩当前一组待练、其后组已跳过，做完这组直接按动作完成后的路径继续其他待练动作，不创建无待练目标的组间休息。
- 排序资格是零完成、零跳过且仍有待练组；跳过标记和批次状态加入现有 `reorderToken`/训练操作基线，过期草稿不能覆盖跳过。
- 进度条继续用实际完成总数 / 本次目标总数；可结束时单独显示“训练可结束”。不增加第二条流程进度。

备选方案：把完成数与跳过数合并计算进度和 `completed`。虽然页面容易达到 100%，但会让实际训练量表达失真，并污染换序和统计语义。

### 3. 跳过与撤销使用单独的事务操作

`skipRemainingSets` 接收会话 ID、预期当前动作 ID 和训练状态基线。确认弹窗基线包含顺序、组状态和当前游标，但单纯倒计时流逝与同一休息自然到期不使基线过期；需要沿用现有写入代数防止旧加载覆盖新结果。

事务内依次验证：会话进行中、动作归属正确且仍为当前、至少一组真实完成、还有待练组；若仍在休息，必须为该动作的组间休息。创建一条跳过批次，更新该动作全部待练组；保持目标组数、完成时间与完成序号；取消当前休息及有效提醒；按本次顺序更新游标。没有待练组时持久化可结束状态，由现有结束弹窗让用户决定保存。整个事务失败时不产生半个批次。

`undoLastSkip` 查找最近未撤销且仍引用已跳过组的批次。确认后验证最新基线，在事务内只恢复该批次组，标记批次已撤销，取消当前休息及提醒，并回到最早恢复的组。下一动作已经完成的组和顺序不回滚。有效撤销入口置于完整动作列表/会话操作中，不依赖短暂 SnackBar；可提供即时快捷入口但不是唯一入口。

现有 `undoLastSet` 不恢复跳过，继续按 `completed_sequence` 撤销。即使撤销使跳过动作的真实完成数降为零，也保留跳过标记与排序锁定；用户可重做被撤销组，或独立撤销跳过。

含跳过组的动作暂时不可编辑本次组数和休息，提示先撤销跳过。这样避免删除跳过组、让目标变化隐式恢复组或破坏撤销批次；普通未跳过动作的本次编辑保持现有行为。

备选方案：通用操作日志统一撤销所有动作。其复杂度超过两种明确操作所需，并会改变现有“撤销上一组”的用户含义。本次保留两类独立记录与入口。

### 4. 用持久化提醒事件表达期望调度与一次消费

新增 `rest_alerts`，至少包含稳定 ID、会话 ID、逻辑休息身份、调度修订号、截止时间、待练动作/组、语言化内容及 `pending / consumed / cancelled / expired` 状态。新增单行提醒偏好记录，默认开启，并记录已解释/请求过的授权状态。提醒偏好使用 SQLite，由 Dart 设置页面和原生接收器共享；主题与语言仍沿用已有 `shared_preferences`。

开始非零休息时，在训练事务中创建逻辑休息和提醒期望状态。调整时间更新同一逻辑休息的修订号及截止时间；换序或换语言更新目标/文案修订，不重置截止。显式结束休息或训练、跳过组、撤销及关闭提醒使事件取消并增加修订，旧 Intent 即便已进入接收队列也不匹配。

自然到期与显式取消必须拆开：当前 `_clearRest()` 被多个路径共用。自然归一化只结束页面休息，不能抢先把同一时刻应送达的提醒取消；显式取消须使提醒失效。提醒接收器不能仅以 `rest_end_at` 是否非空判断有效，要结合逻辑休息/事件状态、修订、启用偏好与会话是否仍在进行。冷启动/重新进入应用时先把已到期未消费事件标成过期，再做恢复，以满足不补播；仍在未来的事件进行调度对账。

每个事件通过条件更新原子抢占一次消费。前台倒计时观察和系统到期广播都调用同一消费入口，只有抢占成功者可触发输出；修订、截止、目标和会话有效性不匹配者只丢弃。允许的系统回调送达窗口是截止后 30 秒，超过窗口标过期。界面每次刷新不尝试为旧截止生成新事件。

消费记录在声音/通知输出前写入，保证至多一次；进程若恰在消费后输出前崩溃，可能漏提醒，重启不重复补播。避免重复优先于承诺崩溃窗口下恰好一次。

备选方案：仅以“上次截止时间”保存在 Widget 内去重。无法覆盖进程恢复、自然到期归一化以及原生后台输出，故不采用。

### 5. 原生 Android 桥负责定时唤醒和统一输出

新增可注入的 Dart `RestAlertService`/平台接口，接入既有 MethodChannel 模式。Android 侧使用 `AlarmManager`、显式不可变 `PendingIntent` 和内部 `BroadcastReceiver`；桥承担调度、取消、查询权限、一次消费、前台短音/回调、后台通知及点击 Intent。后台不启动 Flutter 引擎执行训练逻辑。

- 支持版本按现有 Android 配置判断能力；较新系统使用 `SCHEDULE_EXACT_ALARM` 的用户授权路径与能力查询，不使用自动准许的 `USE_EXACT_ALARM`。可用时采用允许 idle 的精确调度；不允许时回退系统非精确调度并展示“后台提醒可能延迟”，仍应用 30 秒迟到失效边界，不承诺降级模式必达。
- Android 13+ 检查并按需请求通知权限。先保存组完成与截止时间，再提供简短用途说明和系统申请；首次实际使用或用户主动启用时申请，拒绝后不循环弹窗。准时提醒授权是可选的系统设置动作，返回后刷新能力。
- 原生侧只在已完成数据库初始化的现有 v3 数据库上进行提醒相关短事务；不执行建库迁移、不改 `user_version`、不回写训练游标。使用同一 SQLite 文件，处理锁竞争、有限重试与不支持版本的失败；与 Dart 端用事务/修订共同保护竞态。
- App 前台可交互时，统一输出入口使用随应用打包的短声音并回调 Dart 显示提示，后台只发通知并由通知渠道播放同一短音。前台不同时发布带声音的通知。生命周期状态由应用级协调器维护，页面计时器只是前台观察者。
- 前台音频使用通知用途的 AudioAttributes，遵循音量、铃声模式与勿扰策略；后台遵循通知渠道声音设置。不开启持续播放，不暂停或强行覆盖其他应用音频。
- 自定义通知渠道的声音绑定由系统维护，不反复重建渠道覆盖用户选择。无权限或渠道禁用时，不声称后台提醒可用；前台回调与短音不依赖通知权限。

备选方案：引入 `flutter_local_notifications`。通用插件可减少渠道和调度样板，但本次仍需要原生原子消费、后台状态验证以及前台/后台输出仲裁；沿用已有桥可避免同时维护插件回调与第二套原生校验路径。该选择不改变 Flutter SDK/最低 Android 版本；发现版本限制时须先按现有目标修正桥实现，而不能静默提高最低版本。

### 6. 训练提交与系统副作用分离并持续对账

训练事务先提交组/休息及提醒期望，再按事件修订调用原生调度。期望记录就是可重试的副作用来源，不增加通用消息队列。服务在事务提交后、启动恢复、应用回前台和权限/语言变化后对账：只安排未来的当前 pending 事件，取消无效 Alarm 与已经展示的通知。

跨 SQLite 与 AlarmManager 无法保证一次原子提交，故用修订和投递前重新验证弥补：取消 API 失败仍不得让已失效 Intent 播放；进程在组提交后但安排前结束时，未来重开可重试安排。已保存组不能回滚或让用户重复“完成本组”。UI 区分训练保存失败、提醒安排失败和权限不足。

关闭提醒的偏好保存及事件失效是同一 SQLite 事务，成功后才更新界面；失败保留原偏好与事件，不出现“已关闭但后台仍按旧策略响”。重新开启只对仍在未来的当前休息启用新修订，不恢复旧提醒。

### 7. 通知导航及语言由应用层管理

通知载荷只携带可验证的会话/提醒身份，不信任缓存的组位置。冷启动待数据库、语言和 Navigator 就绪再消费点击；热启动复用或打开对应进行中会话。新增应用级导航协调器，重复请求同一会话合并；通知目标已结束、丢弃或不存在时提示失效，不自动打开另一会话。

通知文案从 ARB 在应用侧生成并持久化给原生桥，用户动作名原样保留。切换语言后刷新未发送内容以及渠道的可更新显示名称，但不新增休息、不重播已消费事件。原生返回稳定错误代码，由现有 `error_messages.dart` 生成当前语言反馈，不显示原生堆栈。

### 8. 首版审阅默认与验收分层

用户明确确认的是历史“实际完成 / 本次目标”比例与保留真实训练量。前述讨论提出的两类休息统一提醒、默认开启、轻量确认、直接进入下一动作、独立撤销和排除项在本提案中作为可审阅的首版默认；不把它们描述为用户曾单独回答过的设置。

数据与领域测试覆盖：跳过事务/失败回滚/过期请求、撤销与完成序号、顺序与恢复、两种休息、旧 v1/v2 升级、历史比例与完成统计。服务与原生测试覆盖：身份/修订、并发消费、调度失败、显式取消/自然到期、通知权限/准时能力、前后台仲裁、通知点击。

Widget 测试验证动态数量、确认取消、末动作保存、可找回撤销、真实比例小于 100% 的结束文案、设置失败和双语布局。Android 仪器/真机验证前后台与锁屏、普通进程回收、权限拒绝与恢复、通知渠道、静音/勿扰以及到期前后切换；记录 Android/API、设备、电池策略、是否准时授权、截止与实际送达时间。正常前台/精确授权下以到期后 5 秒内为验收目标，30 秒仅为迟到失效上限，不把它当作准时性目标；省电模式与降级结果单独记录，未达目标须修复或记录交付限制。

## Risks / Trade-offs

- [系统限制精确定时或通知] → 分别表达权限与偏好；授权可用时测试准时调度，受限时明确降级，不绕过系统，不阻断训练。
- [原生与 Dart 同读写数据库] → 原生仅使用提醒表与只读会话校验；短事务、归属验证、条件更新及竞争测试，避免原生执行迁移。
- [自然归一化先清掉休息造成漏提醒] → 分开自然到期与用户取消；事件拥有独立生命周期，冷启动才对已过期事件明确失效。
- [调度、取消与到期竞态] → 稳定逻辑休息身份加修订号；投递前验证并原子消费。已成功发送之后才到达的加时无法收回已经发生的声音，不承诺逆转过去输出。
- [用户误把跳过当完成] → 保留目标与完成比例，历史明确未做组状态，结束文案不声称全部完成。
- [撤销跳过带来两个部分完成动作] → 保留真实完成与本次顺序，优先恢复的当前动作，后续只继续尚有待练组动作；对跨动作完成/撤销建立回归测试。
- [旧版覆盖安装破坏数据或降级] → 使用增量 v3 迁移并测 v1→v3、v2→v3；回滚包仍理解 v3，禁止恢复旧数据库或要求卸载。
- [新增广播或通知入口传入无效身份] → 内部广播不导出、显式 immutable Intent、会话归属检查与失效通知测试，不通过通知创建训练。

## Migration Plan

1. 完成 v3 组跳过、批次、提醒事件与偏好表的建库/增量迁移。保留所有旧主键、快照、完成序号、起止时间、排序及有效截止时间；旧组新增字段为空，不回填跳过。
2. 对旧版正在休息的会话，在首次应用协调器初始化时为未来截止创建提醒事件，按授权能力安排；已到期只恢复待练，不补播。新偏好默认开启，但不因升级启动立即申请权限。
3. 更新训练模型/事务/恢复与历史显示后接入应用级协调器及 Android 桥，确保旧训练页与新服务读取一致状态。
4. 通过自动检查、迁移与集成测试后构建 Android APK，以覆盖安装验证原计划、已存历史、未完成会话和提醒设置。QA 文档记录能力与实际送达结果。
5. 需要功能回滚时发布仍支持 v3 的修复包，可暂时关闭新入口并使提醒事件失效，但必须保持跳过语义、排除跳过的待练查询和历史真实比例。不可直接退回不识别 v3 的旧 APK。

## Open Questions

- 短提示音的最终音色可在设备试听后确定，不改变“一次、简短、遵循系统设置”的行为或任务划分。
- 各目标设备的精确定时与省电模式实际送达分布须在指定 QA 任务中测得；不会把未验证的厂商后台保障作为首版承诺。
